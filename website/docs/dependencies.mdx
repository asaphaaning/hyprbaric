hyprbaric probes its host at startup and reports the result in **Settings → About → System**. Nothing here is configured in TOML. Installing or removing a backend is what changes a capability. Even so, the same catalog decides which controls are live, which are greyed out, and what a failure message says.

Capabilities fall into three tiers:

- **Core**: required for the bar to run at all. A missing core capability is a packaging error.
- **Service**: session services hyprbaric integrates with. A missing service leaves that integration pending or unavailable without affecting the rest of the bar.
- **Optional**: per-feature backends. A missing optional backend greys out only its own feature.

A capability reports **Ready** when every probe passes, **Missing** when an optional capability fails or a single probe fails, and **Partial** when a core or service capability fails more than one probe. The message names exactly what was not found: a command, a filesystem path, or an environment variable.

## Notes on individual capabilities

**Brightness** needs no package on a laptop with a kernel backlight device. `ddcutil` is only required for external DDC/CI monitors, and its discovery and write policy is tuned in [`[brightness]`](./configuration-reference#runtime-policy).

**Screenshots** prefer `grimblast` when it is installed and fall back to `grim`. `slurp` is required either way, because region selection goes through it.

**Notifications** and **System tray** are always reported as available because hyprbaric hosts them itself over D-Bus. Hyprbaric claims `org.freedesktop.Notifications` when it is free and observes an existing owner without replacing it otherwise. Sandboxed applications additionally depend on a selected XDG Notification portal backend. If the panel stays empty, inspect the user session bus and portal selection rather than looking for a hyprbaric notification-daemon package.

**XDG user directories** only affects *where* captures are written. Without `xdg-user-dir`, captures fall back to `~/Pictures/Screenshots` and `~/Videos/Recordings`.

## Packaging policy

The packaging source of truth is [`packaging/runtime_capabilities.yaml`](https://github.com/asaphaaning/Hyprbaric/blob/master/packaging/runtime_capabilities.yaml). The Rust runtime mirrors that contract when it probes the host. Packages should install core and service dependencies as hard dependencies and leave optional backends as recommended or optional metadata, so a lean install is possible and features can be added later.
